# Plan: Fix AI Model Integration for Real-time Updates

## Problem Statement
The user reports issues with LM Studio (glm) and gpt-oss-20b models not working properly together, and information not being updated in real time. The goal is to have both models functioning perfectly with real-time data updates and full data availability for analysis.

## Current State Analysis
- Found LM Studio integration in `src/lib/ia/client.ts` with support for streaming and non-streaming requests
- Configuration is stored in the `ia_config` table (single active config)
- The system uses `model_default` from the active config
- Dashboard caching is implemented in `src/lib/ia/dashboard-service.ts` with 15-minute TTL
- Context building happens in `src/lib/ia/context-builder.ts`
- API routes are in `src/app/api/ia/`

## Steps to Resolve

### 1. Allow Multiple Model Selection
    - Modify the IA config system to support multiple active configurations or allow model override per request
    - Update the frontend/chat UI to include a model selector (dropdown) that passes the selected model in the request
    - The `chatCompletion` and `chatCompletionStream` functions already accept `options.model` override, so we just need to wire this up in the API route
    - **Implementation details**:
        - In `src/app/api/ia/chat/route.ts`, extract `model` from request body (if provided) and pass it to `chatCompletion`/`chatCompletionStream` via the `options` parameter.
        - Update the frontend chat component (to be located/created) to have a dropdown populated with available models (from `ia_config` where `ativo = true` or from a static list) and send the selected model with each message.
        - Ensure backward compatibility: if no model is specified, fall back to the `model_default` from the active IA config.

### 2. Configure Both Models in Database
    - Add two entries to `ia_config` table:
      1. LM Studio with glm-4.7-flash (current working model)
      2. LM Studio with gpt-oss-20b (second model)
    - Only one should be marked as `ativo = true` at a time, or we modify the system to allow selecting via API parameter
    - Alternatively, keep one active config and allow model override via request (simpler)
    - **Implementation details**:
        - We will keep one active config (the glm-4.7-flash) as default and allow model override via request. This avoids changing the active config frequently.
        - Insert a second row in `ia_config` for gpt-oss-20b with `ativo = false` (or true but we will not rely on it being the single active). We can also set a unique `model_default` like `gpt-oss-20b`.
        - The frontend will fetch the list of models (maybe via a new API endpoint `/api/ia/models` that returns all configs, or we can reuse the existing `/api/ia/models` which lists models from the LLM endpoint; but we need to map to our configs). Simpler: we can have a static list in the frontend: ["glm-4.7-flash", "gpt-oss-20b"] and assume both are available on the LM Studio endpoint.
        - Alternatively, we can create an admin endpoint to list IA configs (without API key) and use that to populate the dropdown.

### 3. Enable Real-time Updates for Dashboard
    - Reduce dashboard cache TTL from 15 minutes to a shorter interval (e.g., 30 seconds) OR
    - Implement Supabase Realtime listeners to invalidate cache when relevant data changes
    - Tables to watch: `avaliacoes_desempenho`, `leave_requests`, `reimbursement_requests`, `users_unified` (for profile changes)
    - When change detected, invalidate cache for affected users and notify via SSE/WebSocket
    - **Implementation details**:
        - Option A (simpler): Reduce `CACHE_TTL_MS` in `src/lib/ia/dashboard-service.ts` from 15*60*1000 to 30*1000 (30 seconds). This ensures the dashboard refreshes at least every half minute.
        - Option B (more real-time): Set up Supabase Realtime subscription in a service that listens to INSERT/UPDATE/DELETE on the watched tables. When a change occurs, we can:
            1. Invalidate the IA dashboard cache for affected users (by deleting from `ia_dashboard_cache` where user_id matches).
            2. Optionally, publish a message via a WebSocket or SSE channel that the frontend can listen to to trigger a dashboard refresh.
        - We'll implement Option A for quick win, and note that Option B can be added later for true real-time.

### 4. Ensure Context Data is Fresh
    - The context builder already queries live data, but we should ensure no unnecessary caching
    - Consider adding cache busting based on data change timestamps
    - For real-time feel, we could reduce the effectiveness of any implicit caching
    - **Implementation details**:
        - There is no explicit caching in the context builder functions; each call hits the database. However, if the same user makes multiple requests in quick succession, we could benefit from caching the context for a short time (e.g., 10 seconds). We'll avoid adding caching to keep data fresh.
        - If we want to reduce load, we can add a short-lived cache (e.g., 10 seconds) for the context builder, but we must invalidate it on data changes (via the same real-time listeners). For now, we keep it uncached to ensure freshness.

### 5. Testing and Validation
    - Test both models work correctly with the same endpoint (LM Studio)
    - Verify real-time updates by making changes and observing dashboard/context updates
    - Check error handling when one model is unavailable
    - **Implementation details**:
        - Create a test plan:
            1. Load both glm-4.7-flash and gpt-oss-20b models in LM Studio (ensure the endpoint is running).
            2. Verify that the IA config table has entries for both models.
            3. Test chat with each model via the UI (by selecting from dropdown) and ensure responses are generated.
            4. Test streaming mode with both models.
            5. For real-time updates: create a test user, generate a dashboard, then directly modify a watched table (e.g., insert a new evaluation) and verify the dashboard updates within the cache TTL (or immediately if we implement real-time invalidation).
            6. Test error handling: temporarily point the IA config endpoint to an invalid URL and ensure the UI shows an appropriate error message.

## Deliverables
- Updated IA config with ability to select between glm and gpt-oss-20b models
- Frontend chat UI updated with model selector
- Real-time update mechanism for dashboard data (either reduced TTL or Supabase Realtime)
- Documentation on how to switch between models
- Test procedures for validating real-time updates and model responses

## Implementation Details
- The LM Studio endpoint appears to be running locally (based on logs)
- Both models need to be loaded in LM Studio simultaneously
- The system already supports streaming responses via SSE
- Error handling and tool calling are already implemented
